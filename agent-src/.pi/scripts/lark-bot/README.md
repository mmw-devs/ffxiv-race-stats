# lark-bot 开发规范

本规范定义 lark-bot 子系统的核心开发原则。所有修改必须遵循。

## 1. 分层架构

lark-bot 按职责分为多层：

- L0 Config：启动期不可变常量
- L1 Protocol：飞书 API 适配层
- L2 Ingress：飞书事件入口 + 校验 + 反压
- L3 Routing：inbound / outbound 路由决策
- L4a Broadcast：群聊广播（占位）
- L4b Interactive：会话生命周期 + 任务状态机
- L5 Process：进程级异常处理 + 日志 + 轮转 + 崩溃恢复

业务模块按层放置；跨层调用需审查（例：L2 直接调 L5 是禁止的）。

## 2. 关注点 SSOT

每类关注点必须有唯一入口：

- 配置：所有启动期常量集中一处；运行时禁止二次读取环境变量或硬编码默认值
- 类型：所有运行时数据结构集中一处；新增字段改一处即可
- 日志：所有日志输出走同一门面；不在业务模块直接调底层 fs

不持有全局可变状态；不绕过中间层直接调底层实现。

## 3. 依赖单向

- 业务模块（L2/L4b）不直接 import 进程级设施
- 日志输出统一走共享日志门面
- 进程级实现细节只被共享模块引用，业务模块通过门面访问

依赖图不应出现环。

## 4. fail-closed

异常路径一律拒绝：

- 身份解析失败 → 拒绝
- 注册表校验失败 → 拒绝
- 必填字段缺失 → 拒绝

不静默通过、不容错替身、不降级放行。fail-open 是禁止的反模式。

## 5. 健壮性

每条事件 / fs 写入 / 网络调用必须 try/catch：

- 写入失败只记 stderr，不影响主流程
- 定时器与子进程必须在生命周期内显式清理
- 缓存与反压机制必须存在（队列上限、TTL 等）
- 进程级异常处理（crash handlers + 重启风暴保护）是必须而非可选

## 6. 测试纪律

- CLI 入口必须加守卫让测试 import 不触发副作用
- 测试沙箱下子进程 spawn 不可靠，改用 mock + spy + 直接调入口函数
- 关键路径必须有单测；fixtures 路径走 CI 集成测试
- typecheck 与 vitest 都必须通过才能合入

## 7. 重构留痕

每次重构必须留下痕迹：

- commit message 显式列出被剔除功能与迁移路径
- 跨文件依赖移动必须全量同步（同一逻辑不能在多个文件里残留不同版本）
- 被改文件顶部用 JSDoc 标注演进注释（指向相关 PR / Issue）
- 长期不变的核心架构部分优先保留抽象描述；具体实现细节通过代码自身体现
